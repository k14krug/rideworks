## 3. Gate 1: authoritative SQLite FTP history

### Storage and provenance contract

The product has **one effective FTP timeline composed from two distinguishable entry kinds**; do not create two competing analysis timelines. Use compact FTP-specific SQLite storage, not a generic athlete-state or append-only event system.

- **Original recorded settings:** import all 66 Strava-reported dates and watt values exactly. They stay in the active timeline as **immutable anchors** and are never edited, moved, deleted, or silently superseded on their own effective dates. Preserve their simple source attribution and the validated import marker/digest in SQLite. Since these entries are immutable, a *second* 66-row immutable shadow copy and a general audit ledger for hypothetical edits/deletions of them are **not required**.
- **Supplemental historical entries:** the Owner may insert an effective date and chosen positive integer FTP **strictly between successive original anchor dates**, independent of whether the inserted watts are higher or lower than surrounding anchors. More than one supplemental entry may be inserted in an interval, in date order. Preserve a clear "Owner-supplied historical interpretation" label, created/updated metadata and, optionally, the selected originating Activity/best-20 evidence. An inserted number is not measured physiological threshold or a change to what Strava historically recorded.
- In the combined timeline, each entry takes effect on its calendar date and ends immediately before the next chronological entry. The following immutable original anchor automatically takes precedence beginning on *its* date, so supplemental entries never permanently displace it. Same calendar date as any existing original or supplemental entry cannot be inserted as a second value.
- The Owner may **edit, move, or delete only supplemental entries**, not original recorded anchors. Keep sufficient identification and revision information for safe correction, optimistic concurrency and honest source labels. An elaborate permanent edit log is not a prerequisite; if a small per-entry change history is useful, explain the cost and leave the originals immutable.
- Track a durable combined-history revision/signature used for coherent reads and calculation-cache invalidation. Mutations of supplemental entries and revision increments must be atomic. Do not duplicate the original personal FTP dataset in generated code, tests, JSON, or another CSV.

### Date, validation and unknown-state policy

- Effective from date **inclusive**, until next setting date **exclusive**. Use existing athlete-calendar interpretation America/Los_Angeles independent of browser timezone. Preserve uncertain-source-timezone boundary rules, even when adjacent entries have identical watts. Do not invent FTP before the first known original anchor.
- An added intermediate entry splits the currently effective interval and remains in effect only until the next supplemental or original entry. Editing/moving/deleting a **supplemental** entry adjusts the intervening intervals but **never changes any original setting/date**; a preview should show the actual before/after intervals.
- Reject duplicate-date insertion, especially on original anchor dates. For a same-date supplemental entry, offer a deliberate **edit supplement** action instead. Equal watt values on **different** dates are fine. Do not silently merge or overwrite entries.
- Outside the original recorded history bounds (before the first original date, on/after the last original date), the current task **does not authorize a new supplemental entry**: the Owner explicitly described *between original entries*. Plot otherwise-eligible rides outside those bounds as available evidence; if broader extension is wanted, return to the Owner rather than quietly deciding it. A genuinely new Store with no original history remains usable/empty and does not fabricate any anchors; manual bootstrap/initial-history behavior for that separate case should be documented rather than silently applying this one-rider import.
- Prevent supplemental future dates, validate positive integer watts and canonical dates server-side. Original anchors are read-only, with a source explanation; only supplemental entries expose edit/delete controls.
- Save rejects stale history revisions from other tabs and asks to review the latest interval. Failed actions must not alter history, revision or derived caches.

### Schema, bootstrap and recovery semantics

- **Schema migration is not bootstrap.** New empty Stores get an empty table and a legitimate initialized-empty state, not a copy of the Owner's FTP. Existing pre-upgrade Stores are identified as *migration required* until explicitly bootstrapped; installing the schema alone is **not** success and must not masquerade as intentionally unknown FTP. If detection of an older blank Store needs nuance, document and test it instead of auto-seeding.
- While original files still exist, create an **explicit, narrowly scoped bootstrap command/operation**, taking source path and explicit target store; do not silently bootstrap in normal Store construction or on HTTP page view. Validate equality of the two sanctioned 66-entry files plus approved SHA-256 cb990c18e969d0d12f1d524bea22cf8b596746171f179f6241748394b87ad073, 66 chronological entries, proper inclusive/exclusive bounds, valid ISO dates and integer-positive watts **before starting the import**. Do not import the root 52-row legacy CSV.
- Insert the **66 immutable original anchors** and durable import completion marker in **one atomic transaction**, with exact ordered date/value comparison. Schema state, bootstrap-complete and intentionally empty are distinct. Replaying the completed bootstrap must be a **no-op even after supplemental inserts/edits/deletions**; it must neither add duplicates nor discard supplements. Missing/different source, nonempty unmarked history, conflicting import, partial/uncertain commit or invalid marker must stop and report, never merge silently.
- A new empty Store must work without historical FTP; an **existing** unbootstrapped Store must show a clear migration-required diagnostic and not quietly serve misleading empty-FTP analytics. Bootstrapping is a controlled one-time import, not a permanent hard-coded 66-row seed in source code, JSON or SQL.
- Rollback pairs compatible code **and** DB version: pre-upgrade code cannot read the new schema. Rehearse restore from a consistent pre-migration database plus its matching old release. Preserve current upgraded DB if recovery occurs after edits; restoring an older backup loses later edits unless separately recovered. Never decrement PRAGMA user_version as an improvised downgrade.

### Runtime consumers and calculation consistency

Audit/refactor every current FTP consumer to a store-scoped authoritative DB reader, including:

- training_state.ftp_history/ftp_on/ride_results, per-ride input signatures and training_stress_cache, daily_series/Training State and training_home;
- planning.completed_history, plan's separate current FTP lookup, activity_context and classify_activity, planning_classification_cache, and confirmed planning_intents source context;
- Home's Training State and Plan summaries, Activity Review/planning_page context and current-FTP display;
- legacy verification/diagnostic scripts that directly load packaged CSV history.

An entire request/analysis sees **one coherent FTP history snapshot/revision**. Do not load FTP outside a subsequent write transaction and accidentally mix revisions inside the same request; reuse/propagate one read within the actual Store transaction. A whole-history signature in per-ride cache keys is acceptable initially. Measure full-history cold refresh cost before attempting targeted optimization. The daily 42-/7-day series is recomputed per request; preserve this behavior.

**Behavior to preserve:** normalized power/duration stress scales as inverse-square FTP; current selected stress can switch between eligible power and HR fallback when FTP becomes known/unknown; HR-derived candidates are FTP-independent but the selected method might change. Actual watts, 20-minute evidence, power curves, observed work kJ, source selection and original files do not change. FTP edits may change Planning automatic classification and recommendations, but Owner classification overrides take precedence. Previously saved confirmed intents, their FTP at confirmation, feedback and rider corrections are immutable historical context: do not rewrite. New intents may use current FTP context with an honest DB-history signature/provenance field instead of a misleading CSV hash name. Existing literal wattage targets in planning.recommendation remain **unchanged** in FTP-01; rescaling targets is a separate future policy decision.

## 4. Gate 2: FTP history chart/editor

### Placement and visual evidence

The original anchors remain visible at their exact dates regardless of added entries. The synthetic line endpoint is not a recorded marker.

A new Store with no FTP still supports the graph and manual add.
- Y value for each point: **unrounded 0.95 × that ride's best-20 average watts**. Orange when that exact unrounded value is strictly greater than its comparable dated FTP; gray when it is at/below (ties gray). Compare **before** rounding. Show raw best-20 in tooltip/evidence. For integer editable suggestion use nearest integer watts with 0.5 ties rounding **up**; do not use banker's rounding. The suggestion is an initial value, not a claim of physiological FTP.
- Include eligible rides with no comparable dated FTP (prehistory or uncertain source-date boundaries) in a visually distinct **"FTP unavailable / comparison uncertain"** category; never silently show them gray/orange. Display the reason. Such points remain inspectable/selectable as evidence, but creating a supplemental entry outside the first/last original anchor boundaries requires a separate Owner decision. Orange and gray comparable points between original anchors seed intermediate entries.
- Orange, gray and unavailable categories are togglable. Display dynamic counts and legend; do **not** hardcode 879/69/810, 150, or 66 as permanent facts. Tooltips provide activity/date/source, best-20 watts, 95% watts, matched FTP or unavailable reason, difference when comparable, and link to Activity.
- Provide useful full-history range, zoom into a selected period, pan/date navigation, reset-to-all and at least a date-range control or slider of comparable usefulness to the standalone Plotly chart. Browser/native SVG is preferred if it satisfies selection/zoom/touch/keyboard usability without a 4.8 MiB embedded report; a locally bundled Plotly dependency is allowed only if justified by implementation/test evidence, with no CDN or frozen-data embedding. Do not claim a few presets alone recreate reference zoom/pan.

### Editing behavior

- Selecting an **orange or gray performance dot** in an interval between original anchors freezes the Activity, the editable 95%-of-best-20 suggestion and the *athlete-calendar* activity date. Hover or repaint must not overwrite the pending form; opening the Activity is separate.
- Provide an accessible all-points list/keyboard selection path for overlapping dots. The Owner can also manually add an intermediate FTP entry on any **permitted date between original anchors** without selecting a ride. Points outside the anchored range or with uncertain comparison remain inspectable, with clear explanation when insertion is not authorized rather than an incorrect FTP assignment.
- Existing **original** FTP markers are always **read-only**; there is no edit/delete-original action. Existing **supplemental** markers can be deliberately edited/moved/deleted. All edits preview affected intervals and identify which subsequent **original anchor** resumes control. No action can change or remove an original date/value.
- Before saving an addition, show previous effective FTP, proposed FTP and the next effective entry/date. Lower as well as higher intermediate FTP is permitted. After any save, the combined step line and orange/gray classification update. Explain that later Training State values can change, but do not fabricate a precise preview model delta. Require explicit delete confirmation for supplements and reject same-date collisions/stale two-tab edits.
- Persist using existing Origin/nonce/validation conventions. Validate server-side entry type/identity, associated Activity, permitted date, integer watts and expected revision. No automatic FTP calculation or Strava writeback. Preserve filters, selection, zoom and focus where practical.
