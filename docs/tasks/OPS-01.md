## 1. Fix timezone-dependent startup first (no schema/data changes)

**Confirmed bug:** `/` without `home_tz` currently displays "Enable JavaScript to use your browser timezone..." rather than the real dashboard. Adding `?home_tz=America%2FLos_Angeles` displays the full page. Current `review.js` may redirect browser timezone-specific pages, creating a fragile loop/fallback.

**Approved rule:** Fixed **default rider-local timezone `America/Los_Angeles`**, with `zoneinfo` daylight-saving handling—not a fixed UTC offset. Apply consistently to ordinary **Home, Plan, Training State and date-dependent Activities/Settings** paths that currently need query parameters or client detection to decide calendar boundaries. **Navigating to `/`, `/plan`, `/training-state` (and normal Activities links) must show substantive content on the first server response, without JavaScript timezone redirection.**

- Keep **explicit validated timezone query parameters** (`home_tz`, `plan_tz`, `tz`) working as supported for synthetic tests, reproducible historical checks and special cases. **Only an absent parameter uses LA default**; never silently convert an **invalid explicitly requested** zone to LA and pretend the supplied zone was valid. Preserve existing validation/error behavior for such requests or use a clear 400; do not create redirect loops.
- Remove the generic `data-calendar-timezone` browser-timezone redirect requirement for full server-rendered pages, or constrain JS so it never overwrites an explicitly chosen server timezone. Make normal links usable with JavaScript disabled **as far as server-rendered content is concerned**; interactive SVG graphs may still require JS. Correct the current `review.js` timezone override of bookmarked/explicit zone where relevant, without rewriting unrelated chart sample processing.
- Preserve **UTC instant storage and unchanged activity timestamps**. For normal UI, distinguish calendar computations using `America/Los_Angeles` from source timestamps. Never change the existing power/performance/training/planning algorithms or manually shift records. Watch PST/PDT transitions, year boundaries and other day-change cases.
- Add regression tests: `GET /` with no zone immediately includes the real mileage/Next Ride dashboard and **does not** contain the JS fallback; `/plan` and `/training-state` likewise have real content or honest normal empty states; client JS doesn't force a redirect on ordinary links; explicitly requested valid `UTC`/`Asia/Tokyo` still produces the correct date-scoped results; invalid explicit requests behave transparently; original activity/calendar/FTP/source results remain unchanged. Check full browser navigation with ordinary links and disabled JS for content-only fallback.
- This correction may be built/tested independently of which real store is selected because tests use disposable synthetic stores. Keep it in the same OPS-01 PR for convenience; **do not deploy against a different private store simply to test the fix**.
