# RACE-02 — Improve race screenshot accuracy and require automatic whole-batch matching

**Status:** Pending implementation (Analyst-authored, 2026-11-06).
**Issue:** [#60](https://github.com/k14krug/rideworks/issues/60).
**Predecessor:** RACE-01 was accepted and merged in [PR #59](https://github.com/k14krug/rideworks/pull/59). This is a follow-up, not a rewrite of accepted activity/FIT analysis.

## 1. Purpose and evidence

Improve actual Zwift Racing Profile screenshot extraction, avoid silent incorrect activity associations, and make race-result correction/removal practical in RideWorks.

The Owner reports a screenshot race on **2026-09-27** extracted as **2026-09-29**, causing an automatic-match failure until the date was edited; a **Stage 4** event extracted as **Stage 1**; and poor score/change recognition. The production screenshot was reported as **768 × 939 pixels with 17 visible rows**. These are **Owner observations**, not a screenshot verified or committed in the repo. The earlier RACE-01 [implementation report](../../reports/RACE-01/implementation.md) documents the 11-row test with only 1/11 score and 1/11 change exact matches, and retained incorrect confirmed data. An existing result may need correction.

**Current code inspected as of JIT authoring:** `rideworks/race_results.py` defaults to `gpt-4o-mini`, extracts one image in one request, and `suggested_match` deliberately discards stage tokens and digit-only tokens during title comparison. `rideworks/race_page.py` currently permits manual activity IDs and per-row skip/confirm. The new Owner decisions below supersede those parts **for new screenshot imports**. They do not redefine the FIT/native power model.

## 4. User-visible scope

### A. Extraction model, sectioning and quality

1. **Owner decision:** use exact model ID `gpt-6-luna` as the default screenshot extraction model via the existing server-side Responses API; preserve the ability to configure the model explicitly for diagnostics but do not silently fall back to the previous default. Verify that image input, strict structured JSON output and chosen reasoning/image detail settings actually work with this model. No requirement for a new API client/framework.
2. **Owner decision:** split tall screenshots into **overlapping horizontal sections** for extraction. Retain the unchanged original screenshot and each section's image bounds/overlap, request status, model output and provenance. Evaluate the 768×939/17-row case against a full-image extraction in the Owner gate. Splitting cannot restore absent pixels; do not impose a minimum resolution without evidence.
3. **Revised Analyst guidance after reproducible boundary failures (2026-11-06): DO NOT require or build a perfect pixel-derived physical-row counter, separator detector or model-coordinate identity oracle.** A clipped last row and a row-like heading caused 16/17 and 18/17 counts in [the synthetic investigation](https://github.com/k14krug/rideworks/blob/task/race-02-screenshot-reliability/reports/RACE-02/implementation.md). The prior proposed source-row-ownership requirement is withdrawn as an implementation prerequisite; it is not justified by the evidence. No silently authoritative image-derived row count is permitted.
4. Use a **simple deterministic overlapping tile plan** based on source image dimensions, not inferred physical row boundaries. Choose overlap large enough to normally show an entire row on at least one tile (including wrapped titles) while still increasing readable detail; test edge cases at tile seams. Model extraction yields **observations**, with originating tile/order retained. The instruction may request only fully readable rows within a section, but the app must not assume the model always obeys that or returns correct positions.
5. **Never automatically discard an observation** merely because it agrees with another on date/event/score/text, model-provided coordinates, source-pixel borders, or a candidate Activity ID. Surface potential duplicates across neighboring overlapping tiles as **unresolved observation groups** and show both original crop contexts. Different values from apparently repeated observations are a conflict, not a signal to select one guessed value. Keep all raw extraction outputs.
6. **Explicit extraction-reconciliation review:** before any batch commit the Owner verifies the number of **visible physical race rows** in the uploaded screenshot (not the `RACE RESULTS (33)` heading), and reviews/marks which adjacent-tile observations are duplicate views of the **same** physical source row. This is **manual source-observation reconciliation**, not manual Activity matching. Allow an explicit, clearly labeled 'Same screenshot race row as observation X' action only with both original crop images available; preserve both observations and the reconciliation decision in import provenance. Different physical rows, including ones with identical extracted text, must stay distinct. If observations disagree, the owner must correct the final race fields from the screenshot. Never silently choose a value from conflicting observations.
7. **Commit gate:** the final reconciled distinct-race count must equal the Owner-confirmed visible-row count; each observation must belong to exactly one distinct reconciled race; no unresolved duplicate/conflicting observation; each distinct race must automatically match a unique Activity under section B; any uncertainty or section/API failure blocks **all** confirmed-result writes. Confirming a visible-row count does not establish model transcription accuracy; the owner still reviews all eight fields. The Owner may abandon/retry with a better image or shorter separate screenshots; a smaller screenshot is a **new separate batch** with the same strict matching gate.
8. Avoid overengineering a general OCR/row-segmentation engine. Any apparent automatic duplicate grouping is only a **suggestion**, never a silently applied deletion. The interaction should be compact and make the rare ambiguity easy to resolve. Preserve upload resource bounds and no API calls before the Owner clicks Extract.

**Boundary of the Owner decision:** the Owner's all-or-nothing requirement applies to **distinct races after transparent screenshot-observation reconciliation**, not every redundant model observation from an overlap. The ability to confirm two observations are one physical source row does not authorize skipping a real race, manually selecting a ride, or saving an incomplete batch.

### B. Whole-batch **automatic** activity matching

**Owner decision:** every distinct extracted race must automatically match **one and only one** existing RideWorks Activity. If even one extracted row is unresolved, **the entire batch is blocked**. No race-result inserts, updates, deletions or replacements from that batch occur; no partial success. Manual picking an Activity ID or skipping a row must not bypass this requirement.

The intended review loop:
1. Show all extracted/normalized fields, their original screenshot context and independently computed match status/evidence.
2. On **every** change to date/time/event/group or other relevant field (or screenshot display timezone), recompute the **entire** candidate set and automatic matches. A client-side preview is optional, but the **server recomputes** on review and again inside the final commit transaction; never trust a submitted hidden match/OK flag. Do not retain a stale match from before an edit.
3. Only if **all** distinct screenshot races after section-A observation reconciliation have one unambiguous qualifying automatic match, the Owner-confirmed visible-row count agrees, and no source/overlap conflicts remain may the explicit **Confirm Batch** action enable/commit. The Owner still reviews all fields and approves replacements; a match is not proof that every OCR value is correct.
4. If blocked, display exact row numbers and reasons (no match, multiple candidates, missing/invalid date/time/timezone, title/stage conflict, collision with another row's Activity, overlapping-section ambiguity or existing-result conflict). Offer nearby activities/dates/times **as diagnostics only**, not a way to manually force acceptance. The Owner can correct the extracted fields and run matching again, or abandon/retry with a better screenshot. Do not auto-change source values or a date to make a match pass.
5. Explicitly parse and compare stage-number evidence. When **both** the screenshot event and Activity title have a stated stage number and those disagree (e.g., Stage 1 vs Stage 4), matching is vetoed, even with same-day/time/title overlap. If either lacks a stage number, it is not automatically a conflict, but the remaining title/time evidence must still be sufficiently distinctive. Generic series words alone ('race', 'zwift', 'stage', 'z racing', sponsor names) are not adequate proof. Preserve legitimate truncated titles without inventing their omitted text.
6. A sufficiently close start-time window may help identify a candidate, but a ten-minute window does not justify overriding a title/stage/date conflict. Handle date-effective screenshot timezone and DST ambiguity. Nearby wrong-date or near-time candidates may be displayed to diagnose OCR errors, **never auto-linked across a date conflict**.
7. Reimported unchanged results linked to the correct Activity count as already matched and do not require duplicate writes. Changed records require explicit replacement approval. If a result is already attached to the **wrong** Activity, don't leave two active records for the same race or silently transfer links: surface the conflict and require explicit correction/removal of the old attachment, retaining provenance, before a final whole-batch import. **Implement the cross-import source-identity rules in section B.9 below; checking only records whose stored OCR date equals the newly corrected date is insufficient.**
8. Multiple model **observations** of one physical screenshot race may be explicitly grouped by the Owner after comparing the source crop contexts; only that **reconciled distinct race** is subject to one automatic ride match. This is not a skip action or manual activity selection. Unresolved duplicate observations, an unchecked/mismatched visible-row count, or two truly distinct races competing for one Activity **block the entire batch**. Preserve every raw observation and the Owner's grouping/correction decisions.

9. **Cross-import possible duplicate / wrong attachment policy (Analyst correction after PR #61 synthetic failure, 2026-11-06):** Compare every new **automatically matched** distinct race with active race results linked to *other* Activity IDs, using **source provenance first** and cross-date candidate evidence second. Race identity and Activity identity are distinct; a previous bad OCR date must not hide a wrong attachment.

   - **Same original image:** Compare original screenshot SHA-256 and surviving import/reconciliation evidence, including Owner-reviewed source-row order/group provenance if available. Same image hash by itself is **not** proof that two results are the same race—the screenshot contains many rows. When a unique physical-row correspondence is supportable, an active record on a different Activity is a **blocking conflict**. Where older records lack reliable row-level provenance (including legacy RACE-01 imports), show the suspected pair with source context and mark identity **unresolved**, not automatically identical or different.
   - **Different screenshot/crop:** There is no universal race ID in the screenshot and exact event names/start times can recur. Search a bounded, documented neighborhood around the race date (initial candidate guidance: **±3 calendar days**), plus same/near local start time (within **10 minutes**) and distinctive event/series wording, with stage number, race group, finishing place, score and watts only as supporting or contradictory evidence (many of those can be misread). Do **not** infer identity solely from event/time/title, even if stage matches. Such a pair is an **Owner-review candidate**, not an automatic duplicate or a reason to delete an unrelated legitimate race. Widen candidate evidence when the preserved source images clearly establish identity; do not claim every possible historical OCR error can be detected heuristically.
   - **Review resolution:** On a possible prior association, show the current candidate, old linked Activity and result, both activity dates/times, and original screenshots/import provenance when available. The Owner explicitly chooses **“Same race — correct old attachment”** or **“Different races — retain both”** after comparing evidence. This is **source identity review**, NOT manual selection of an Activity ID, and may be recorded with the current import reconciliation in existing provenance infrastructure; use a minimal additive store field/table only if necessary. An unresolved identity decision blocks the entire batch.
   - **Same race:** Never silently reassign or remove the old result. Block the whole new batch, identify the existing incorrect association, offer the separate confirmed **Remove race result** action (history retained), and require fresh validation of the full batch after removal. Do not remove the old result as a side-effect of a failed batch or allow Owner acknowledgement to bypass required automatic matching.
   - **Different races:** Record the Owner's explicit, scoped decision and preserve both active records. A subsequent commit must verify the referenced old result/revision and the new source identity have not changed (stale decision => review again). Do not persist a blanket exception for matching titles across other race dates/imports. Every new race must still automatically match one unique Activity and pass all-or-nothing checks.
   - **Limits:** Where provenance and visual evidence cannot distinguish the two races, remain blocked and report uncertainty; do not invent a stable cross-screenshot ID, widen a fuzzy-match threshold until everything blocks, delete an unrelated recurring race, or claim impossible certainty. The system may display candidates conservatively, but must not call them proven duplicates.

**Conflict with RACE-01:** the previously accepted manual-ID, partial skip/confirm, or 'confirmed selected candidate' pathways may remain useful as internal diagnostics/history but must **not** provide a save path around the new all-or-nothing automatic validation for new screenshot batches. This is an explicit Owner supersession.

### C. Cost disclosure and provenance

1. **Owner decision:** after extraction and before final confirmation, display an **estimated API cost** derived from recorded token usage and applicable `gpt-6-luna` model pricing. Label it explicitly 'Estimated API cost', not 'Amount billed'.
2. Record each attempted section request's model, prompt/schema version, input crop bounds, token usage fields (including cache fields if returned), status, and any available API request identifier; summarize the completed and attempted requests for the import. Retain only privacy-appropriate metadata and original/source evidence locally.
3. Use a documented, versioned pricing snapshot (model, processing tier, effective/access date, input/output/cached rates) and compute `sum(section_input_billable * rate_input + section_output_billable * rate_output) / 1e6` adjusted for actual reported cached/noncached inputs. Reasoning tokens may be part of output usage; do not double-bill them. Retries count when usage is returned; failed attempts with unknown usage produce a **possibly incomplete** estimate, not a false zero. If fields/rates are missing, label cost estimate unavailable/partial. Avoid rounding a small positive estimate to '$0.00'; use adequate fractional-cent display or '< $0.01'.
4. Keep credentials server-side, use the existing prompt privacy/opt-in statement, don't include image bytes or tokens in logs, and do not submit screenshots to any service without Owner-triggered extraction.
5. Check current official OpenAI API model support/pricing rather than assuming past quoted prices. At JIT creation, official published Standard rates for `gpt-6-luna` are **$0.10 / 1M input** and **$0.50 / 1M output**, with **$0.01 / 1M cached input**; these are reference values, not immutable constants or proof of billed costs.

### D. Correct and remove race results

1. Preserve re-import and explicit replacement of incorrect stored values, without erasing prior values/import/source evidence.
2. Add a **Remove race result** control for each saved row in the Race Results table, with a specific confirmation naming the race and linked ride; require normal origin/nonce checks. The removal unlinks/deactivates **only** the Race Results association. It must not delete the Activity, FIT, existing activity metrics, preserved screenshot, imports or revision history.
3. Store the removal/tombstone action and timestamp with sufficient provenance to explain what was removed and from which Activity; prefer a minimal additive migration consistent with the existing SQLite schema. After removal, both Race Results and Activity Review must stop showing an active link; source/revision history remains recoverable/inspectable. Reimport after removal must be explicit and idempotent, not a silent resurrection.
4. Removal is a separate Owner-confirmed correction action; it is not a per-row shortcut for an unresolved **new** screenshot batch. Failed all-or-nothing batches must have zero mutations to confirmed race data.

### E. Activities browser

On **Activities** page, show **Racing Score** and **Race avg watts** for a linked, active race result. Keep the existing activity average-power metric and evidence source unchanged; use distinct column/label names (e.g. 'Activity avg power' vs 'Race avg W') and clearly distinguish missing race values from zero. Keep pagination/filtering/sorting and responsive behavior; make a bounded query for visible rows rather than N+1 expensive full-history scans. Do not change Home, Performance or training-state calculations.

## 9. Stop-and-report conditions

Stop rather than invent policy if: official model/API requirements cannot be met; screenshots cannot be divided so complete rows are readable in at least one crop; section observations cannot be **presented for explicit Owner reconciliation** without losing evidence; the strict physical-row-count confirmation / all-or-nothing automatic matching cannot be enforced; source identity review cannot safely distinguish an earlier incorrect attachment from legitimate recurring races without risking a wrong unlink or duplicate active result; stage conflicts cannot be checked without unreasonable false negatives; record removal could damage source/provenance; saved incorrect records cannot be safely corrected; estimated usage is materially unknowable; the Owner's actual data needs migration or repair not explicitly authorized; live tests show unexpected accuracy/cost; or a requirement conflicts with current accepted RideWorks policies. **Do not stop solely because an automated separator heuristic fails the clipped-row or heading tests: it is no longer required.** Propose the smallest remedy and request Analyst/Owner direction rather than bypassing the whole-batch rule.
