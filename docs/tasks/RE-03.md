# RE-03 — Strava Relative Effort numeric scores with fixed colors

**Status:** pending — Analyst-authored JIT, 2026-10-29.
**Starting point:** refreshed `main` after accepted RE-02 / PR #53.
**Allowed Invocation:** `/TASK only`.

## 1. Purpose and Owner decision

Replace the relative-to-recent-history effort dots and category pills on RideWorks Home, Activities, and Activity Review with **Strava's own per-activity Relative Effort number** (`suffer_score`), colored using **fixed score thresholds**. A given number must always have the same color, regardless of ride date or the user's recent workload.

The Owner explicitly prefers this simpler presentation, is not concerned with comprehensive historical backfill, and wants RideWorks Fitness/Fatigue/Form and underlying modeled training stress left separate and unchanged.

**Supersession:** This RE-03 decision overrides RE-02's 42-day percentile-based *presentation/classification* for these three surfaces. It does **not** undo RE-02's integration acceptance or authorize changing training-state, FTP, HR or source-selection calculations.

| --- | --- |

## 4. Scope and implementation

1. **Confirm live API availability using a small bounded recent check.** On an authorized local connected Strava environment, inspect a small recent cycling sample (for example, recent 30–60 days, preferably from already-synchronized observations and only a bounded targeted fetch where needed). Check whether `suffer_score` is present, null, or missing; validate score type/range and rough distribution from the authenticated API response. A comparison with Strava's logged-in website is optional diagnostic evidence, **not an implementation prerequisite or stop condition**. Do not require a browser login, session cookie, or a user-shared signed-in page for RE-03. **Do not commit private payloads, activity titles/IDs, locations or tokens.** Summarize only sanitized counts/distribution, or report that private validation was unavailable. Do not crawl historical API data.
2. **Accept and preserve API score evidence.** `rideworks/strava_api.py` currently filters out `suffer_score` via its `NUMBERS` allowlist. Extend normalization to accept only valid nonnegative numeric score representation consistent with Strava's API (including documented null) and preserve it in the current API observation evidence. Keep provenance: it is a vendor score, **not** RideWorks modeled training stress. Preserve absent, null and numeric zero as distinguishable cases where the source permits.
3. **Use existing activity-source association.** Read the current associated Strava API observation for a ride; do not match by ride name, invent a score from power/HR, or substitute locally calculated stress. Minimize code/schema changes. Existing API snapshots without the new field may remain missing until a targeted refresh.
4. **Bounded recent score acquisition.** Existing forward sync covers recent/new activity observations. Provide only the minimum reasonable way to refresh a small recent cohort of already-associated rides (or reuse an existing targeted summary-enrichment path) so newly admitted `suffer_score` is useful immediately. Do not backfill years, silently request hundreds of historic details, change sync checkpoint incorrectly, or bypass API limits. Missing values remain missing.
5. **Fixed-color presentation.** Use the same one score and fixed thresholds on:
   - Home Recent Activities: replace effort-color dot with a compact colorized number that does not break titles, row-count fitting, or card height.
   - Activities list: replace current relative-history label/dot pill with a colorized number, preserve links/filter/sort/paging and tablet/mobile readability. If numeric sorting is offered, sort on the numeric score, not its text.
   - Activity Review: replace the old percentile-based Relative Effort breakdown with a compact clear Strava Relative Effort score/source presentation; no fabricated load/intensity split or 'previous 42 days' text.
   - No score: neutral dash with accessible 'Strava Relative Effort unavailable' explanation. **Zero is a valid score and must display as 0**, not missing.
   - Provide accessible text for numeric score and color category. Color must not be the only signal.
6. **Keep other model outputs unchanged.** Do not use Strava's `suffer_score` as power, RideWorks modeled training stress, CTL/ATL/Form, FTP, training-plan inputs, or historical best-power eligibility. Do not recalculate these models to make scores match Strava.

## 4A. Analyst unblock — score-only summary revisions (2026-10-30)

**Review of Dex's mandatory stop:** Accepted; the disposable-store regression identifies a genuine source-identity coupling. A new API observation containing only a newly admitted `suffer_score` obtains a new `strava_api_sources.source_id`, and changes `strava_api_activities.current_source_id`. Existing Strava time/power/HR streams remain associated with the previous summary source ID. Exact source-ID equality then incorrectly treats those unchanged streams as unsuitable for Performance, Power Curve and Training State. The partial implementation is still uncommitted on `task/re-03-strava-relative-effort`; this note authorizes a **narrow correctness fix** and resumption of RE-03, not a new training model.

**Authorized resolution (no schema migration required):**

1. Define **one shared, explicit score-only summary compatibility test** in the Strava stream evidence/selection boundary. A saved stream is compatible with the latest summary if it is associated with that exact summary **or** the stored summary observation it was fetched against and the current observation belong to the same established Strava activity and their **entire normalized source-value dictionaries are equal after removing only the `suffer_score` key**. Absence/null/changes of `suffer_score` may differ. Do not ignore differences in other fields, including `start_date`, `device_watts`, activity classification, moving/elapsed duration, HR settings/availability or any other existing observation field. Never rewrite old evidence, reassign existing stream `summary_source_id`, or forge source identity. Preserve old and current source IDs in provenance.
2. Wire this shared compatibility result into **all** consumers that currently require exact summary-source-ID equality for API stream eligibility or reuse: `rideworks/performance.py`, `rideworks/power_curve.py`, `rideworks/training_state.py` (power and HR stream paths) and `rideworks/strava_streams.py` (reuse/enrichment). Keep existing timing, source-quality, device-watts, file precedence, start-context, pairing, duration and confidence checks intact. A genuine non-score summary change must retain current conservative stale behavior.
3. A score-only API refresh still creates a new legitimate summary snapshot, so existing `performance.input_signature` may be invalidated **even though the stream itself remains compatible**. After bounded refresh writes, use the existing `converge_performance` mechanism when needed so visible Performance does not remain stale; do not suppress cache invalidation with a broad signature rewrite. The calculated best-20, power curve, selected training stress, Fitness/Fatigue/Form and plan outputs must remain numerically consistent. It is acceptable for versioned caches to recalculate from unchanged evidence; it is not acceptable for a score-only refresh to discard a previously eligible ride.
4. **Preflight the bounded targeted score refresh before modifying existing current summaries.** If a refreshed normalized API response differs from its stored current summary in fields **other than** `suffer_score`, do **not** pretend it is score-only or silently make the existing stream eligible. Skip that targeted score update safely, tally a sanitized skip reason, and report the number. If this affects many recent rides or blocks useful RE-03 coverage, stop for Analyst review with aggregate evidence. This limitation applies to RE-03's **targeted score-only refresh**; normal incremental Strava synchronization keeps its established behavior.
5. If score-only compatibility cannot be established safely without a schema or broader source-model redesign, return to Analyst review rather than weakening the checks. Do not force-refresh scores by invalidating existing power evidence.

**Focused regression requirements before resuming the normal RE-03 tests:**

- Build a disposable API-only Virtual Ride with linked, qualified power/time/HR streams and stored eligible best-20, power curve and selected training-stress state. Change **only** `suffer_score` through a new summary observation. Verify stream reuse without another stream request; same numeric best-20, power-curve points, HR contribution, selected load and modeled training outputs; and `performance_history` converged/current after the bounded refresh. Include missing-to-value, value-to-value, and value-to-null score revisions.
- Prove that changing the original summary's `start_date`, `device_watts`, duration or classification **still blocks old-stream compatibility**. Verify a distinct external activity cannot borrow another ride's stream. Existing source ranking and file-backed precedence must not change.
- Verify a targeted response with non-score changes is skipped without updating the current source, sync checkpoint or old streams; sanitized count is reported.
- Then rerun the previously passing 213 focused tests, remaining full suite, synthetic browser widths, and the remaining checks from Section 6. Report observed passes/failures, not merely intentions.
