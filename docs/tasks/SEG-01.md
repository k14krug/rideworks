# SEG-01 — Saved watched Strava segments and Sync updates

## Purpose and Requirements Used
[Product requirements](../PRODUCT_REQUIREMENTS.md); Owner-approved watchlist and one-click Sync from Home or Admin; [Strava API reference](https://developers.strava.com/docs/reference/) and [API terms](https://www.strava.com/legal/api_policy). Owner chose durable personal history over live-only lookups and accepts the retention trade-off; do not treat that choice as an API exemption. Targeted user-selected imports only, no broad historical ride scan.

## First gate: prove one segment in Dev
After HOME-UI-08 is accepted and integrated, use the Owner-provided Tempus and Titans Loop activity-effort link from the conversation as private test input (obtain it locally from Owner if not available; no IDs or payloads in Git). The Owner estimates about 60 rides; this is not an expected exact effort count. The URL is not a canonical segment URL: verify the effort and obtain the actual segment ID from authenticated response data (effort detail or the known activity detail as appropriate); do not pass the URL suffix as segment_id by assumption. Use the existing connected athlete; per-segment effort listing is documented as subscription-required. Run a bounded read-only Dev probe for this segment alone. Check a known recent effort and an older visible effort, exact elapsed time, linkage to an existing ride by Strava activity ID, and retrieval beyond the default 30 results. The documented list exposes per_page and date bounds; verify actual completeness behavior, do not assume undocumented page support or treat a capped response as complete. Report only sanitized counts, coverage, match quality, requests, and any access/visibility limits. No production changes or app implementation before HARD — Analyst review of probe. If access or history completeness cannot be established, stop; no silent fallback to scanning the archive.

## Implementation after probe clearance
- Add a small watchlist with add-by-Strava-link for public segments the rider chooses, including ones they did not create. Distinguish canonical segment links from activity-effort links; resolve/validate before saving or explain an unsupported input. No automatic starring or Strava writes.
- Import available efforts for that one segment on add using the verified bounded approach. Persist Strava provenance and effort identity, elapsed time, date and source activity link; use a RideWorks ride link when deterministically matched. Keep unmatched efforts and allow later linkage. Save idempotently by effort ID, including distinct attempts on the same ride. Latest, fastest imported, and dated effort history must display from saved data without live Strava calls. Be explicit if history is incomplete.
- Extend the shared Home/Admin Sync action to refresh recent efforts for watched segments after ride sync, including when no new rides arrived. Use overlap and per-segment progress or an equivalent retry-safe mechanism; never advance past an incomplete or failed interval. Preserve committed rides and saved efforts if any segment fails; surface a partial result with enough detail to retry. The Home new-ride alert is not a segment freshness check.
- On Home's recent-ride list and on Activities, show a linked count for rides with saved matched watched-segment results. Count distinct watched segments, not attempts; a repeated effort is still shown separately in history. Use a label such as “1 tracked segment” or “2 tracked segments”; omit zero rather than implying that a ride was checked exhaustively. Open the Segments screen filtered to that ride, showing its saved efforts and offering a clear way back to the full watchlist. Calculate counts from saved links only, with no Strava request from either list. Verify both links, duplicate attempts, unmatched efforts, and mobile layout after probe clearance.
- No leaderboard, GPS matching, archive-wide scan, production backfill, or rate-limit workaround. Do not change original ride records.

## Verification and outputs
After clearance, draft PR and sanitized report. Test old-history retrieval beyond one batch, retry/dedup, multiple efforts per ride, unmatched and later-linked efforts, no-new-rides sync, partial failure and recovery, and loading saved history without Strava. Verify both buttons in Dev with the same watchlist; check existing ride sync behavior and data preservation. Use synthetic fixtures and keep private data and credentials out of Git.
